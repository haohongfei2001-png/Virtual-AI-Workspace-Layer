# VAIWL v2.8 核心机制候选：主题创建、稳定组织与自适应显示

状态：**PROPOSED_FOR_OWNER_REVIEW / NOT_IMPLEMENTED**。2026-10-12。
基线：PR #14 `0b07455a09b4f2ae2d756ffca5a868305815e424`；main仍为初始化提交。本轮仅文档，不启动测试浏览器、模型或原生写入。

本文件是三项机制的唯一规范入口；交互、数据、技术、安全与验收分别由同目录对应专题展开，[DEVELOPMENT_PLAN](DEVELOPMENT_PLAN.md)仍是唯一A–G路线。它不是第二个产品或并行开发计划。**提出候选不等于用户已批准全部默认值；合并文档也不能替代运行权限或真实宿主证据。** 当前代码仍是v2.7，直到相应决策批准并逐项实施。

## 1. 统一模型与替代范围

主题（Workspace）是稳定的工作对象与意图容器；窗口（ConversationRef）是一个原生对话的引用，不是Chrome tab；原生Project是ChatGPT的实际项目及上下文对象；Workset是用户当前要一起使用的引用集合。四者不相互冒充。

三条独立轴：**是否成立 → 如何组织成员 → 在哪个区间显示**。主题可先存在再有窗口；成员可跨原生Project；活跃跨度可改变，但不能借此拆合主题、改变成员或原生上下文。

保留v2.7：主题级卡片/紧凑窗口、主页不整卡折叠、左侧旧窗口展开、侧栏开合由用户控制、阅读区唯一无字返回、原生输入/消息/模型/工具/动效所有权、手工意图优先、scope隔离、主题只出现在其最近可靠活跃的一段。日期、来源、数量和“自动·14天”不重新常驻主界面。原生功能原本需要显示的上下文和权限提示不删。

定向替代：固定30日改为**有效跨度H**；H的候选为7/14/30/60/90当地日历日。补齐主题内原生Project/新窗口流程、主题出生及拆合规则。旧v2.7原件与既有测试结果不回写。新建原生Project是新增明确授权的原生动作，不是“投影不改原生”的隐含例外：**普通派生操作仍不改原生；只有独立确认的创建流程可创建目标Project及打开其新聊天入口。**

## 2. 主题内新建：推荐“首次确认、按需建Project、以后复用”

### 2.1 严肃比较

| 方案 | 收益 | 问题 | 选择 |
|---|---|---|---|
| 每次建主题就立刻建原生Project | 原生结构很快一致 | 空项目泛滥；自动发现主题会产生真实写入；上下文变化被隐藏 | 不采用 |
| 首次点击新窗口无提示建同名Project | 最少操作，接近用户构想 | 不明确的真实写入、同名冲突、共享/记忆/工具差异 | 不作为静默默认 |
| 仅派生文件夹，不支持原生Project | 易保持只读 | 回避用户需要的真实项目功能 | 不作为完整解法 |
| **首次确认后惰性创建，后续使用已绑定目的地** | 原生结构与低管理成本兼得；无AI也成立 | 需要可靠目标和分阶段回执 | 推荐候选D28-01 |

### 2.2 正常路径

主题卡头/侧栏主题的按需“＋”表示“在此主题新建对话”，不是展开/拆分。首次没有已配置目的地时，打开轻量选择：主选项“在同名 ChatGPT 项目中开始”；另可明确选择已有Project或“仅归入此主题”。**不先替用户建Project，再询问是否同意。**

选择同名项目时，一次确认明确：当前原生账户/组织、计划Project名称、原生隐私/共享/记忆与工具能力、只创建一个Project、打开一个新聊天入口、**不会移动旧聊天或自动发送消息**。名称取用户确认时的主题名称快照；原生名称限制导致的截断或改写必须再次可见，不能偷偷替换。

现有能力的使用后果由真实原生确认区呈现，不统一强制project-only记忆模式；这可能影响可用工具。实际选项未核验时暂停，不擅自改变用户原生偏好。确认后：核对能力与权限 → 创建Project → 读回稳定Project身份及属性 → 保存关联/默认新建目的地 → 进入该Project原生新聊天输入区。只有宿主真实保存对话并提供可验证ID/Project归属后，才建立引用和当前主题的人工Placement。空输入页只是待建立窗口，不编造conversationId。

后续“＋”使用该主题明确选择的默认Project，不再反复询问同一个决定；每次仍核验当前scope/目的地可用性。默认Project被删、共享状态/权限或关键上下文改变时重新确认，不静默建替代项目。原生全站“新聊天”保持原有行为，不附带VAIWL创建Project。

### 2.3 不可偷换的语义

一个主题可以引用零个、一个或多个原生Project；一个原生Project也可以被多个主题引用。**关联Project集合 ≠ 新聊天默认目的地**：每主题最多一个当前默认目的地，也可以是明确的普通聊天或每次询问。浏览过哪个Project、哪个成员排第一、名称相同，均不构成默认设置。

已有PAIA开发/设计/想法窗口仍留在各自原生位置。首次建“PAIA”Project只影响未来选择此目的地的新窗口，不搬旧窗口、不复制文件/指令、不令所有引用共享上下文。两个主题使用同一Project时原生上下文可能互通，不能宣传为两个隔离项目。

主题改名只改派生名称；Project改名只更新原生观察。已关联ID不变，既有Project不自动跟随改名。另行同步名称属于独立原生改名提案，不包含在本轮创建授权。拆分/合并主题不拆合Project，也不自动创建Project。

同名Project：列出经核验的候选让用户选，不能仅按名复用；用户确认创建新对象时可以同名或选择新名，遵循真实宿主限制。权限不够、访客/临时会话不适用时说明受限，保留显式派生或原生手工路径，不能把虚拟对象称为已创建原生项目。

### 2.4 真实动作不是本地事务

CreationIntent记录请求ID、主题revision、scope/epoch、计划名称/目的地、用户确认摘要、每阶段回执和审计边界。默认预算为**1次Project创建派发、1次原生新聊天入口打开、0次自动发送/移动/删除/分享**；跨重启、标签页、目录和重试累计，不因另一次运行重置。

预算所有者是本次任务的持久控制器，不是临时页面或测试Profile。产品在同一安装的多tab/worker间可共用同scope账本；彼此独立且未协调的浏览器Profile/设备之间，不能靠各自IDB承诺全局去重。没有受支持的跨实例幂等或协调证据时，只允许一个已确认的执行实例，其他实例须重新核对原生对象，仍不承诺远端exactly-once。测试runner自行创建的新Profile不得改变其任务总预算。

状态：DRAFT → REVIEW_REQUIRED → AUTHORIZED → PROJECT_DISPATCHED → PROJECT_VERIFIED → COMPOSER_OPEN → CONVERSATION_VERIFIED → PLACEMENT_COMMITTED。旁路有CANCELLED、BLOCKED、CONFLICT、UNKNOWN_RECONCILE、PROJECT_ONLY、PLACEMENT_PENDING。

操作发出但结果未知，先只读核对，**不自动重发创建**。Project已建但后续失败，保留原对象及其ID，不“回滚删除”；对话已创建但本地Placement失败，仅幂等修复本地关联，不再新建聊天。取消空输入可留下原生空Project，清理须另行用户动作。

预期的原生页面跳转不等于账户授权可以无条件沿用：每阶段重新取得当前文档绑定，只在同一已验证scope、未过期且未撤销的任务许可、明确预期路由/对象及剩余预算均成立时继续。账户/组织变化直接撤权；意外导航暂停。页面跨转不复用旧document token，也不因换token重新获得创建次数。首次消息已存在但时间未证实时，可以保存已核验引用/人工归属而保持时间UNKNOWN，不能为完成流程伪造活跃。崩溃恢复不自动恢复grant；旧的稳定回执帮助确认事实，但不能成为新的执行许可。

真实宿主无法实现可靠自动创建时，保留相同流程的**原生UI辅助模式**：用户在原生界面完成创建，扩展仅在身份/结果可验证后建立绑定。自动化未验证不能成为只读组织功能停用的理由；也不能以辅助模式冒称自动创建已通过。

## 3. 主题生命周期：一个窗口完全可以成立

| 来源 | 是否可建立主题 | 默认行为 |
|---|---|---|
| 用户主动“新建主题” | 可以，0窗口也可 | 创建稳定ID、人工名称/锁；不建原生Project、不制造发送 |
| 用户将一个已有窗口提升为主题 | 可以 | 原生窗口不动；创建主题+Placement以一个可撤销本地计划提交 |
| 从主题内新开窗口 | 不新建第二个主题 | 成功核验原生对话后直接归入发起主题，不等待AI |
| 原生Project导入/关联 | 可以作为建议来源 | 显式选择是否形成主题；不强制所有Project对应一张卡 |
| 内容识别建议 | 单窗口或多窗口均可 | 明确工作对象/目标；首次新主题建议预览，不凭数量硬建 |

**数量不是资格**。单窗口只要用户主动组织，立即成立；自动建议的单窗口若有清楚的独立事项/成果，也可成立。一次性短问、泛泛的“AI/工作/生活”、引用到一个产品名，不应都制造新主题。

空主题是独立持久资产，默认无可靠活跃段。创建后在本次上下文显示一张待开始卡；跨会话通过搜索/管理/固定访问。这个短期可达例外不纳入活跃计数，不复制到历史段；用户明确固定时保留快捷访问。首次可信发送才可能进入活跃投影。近期无输入的人工主题不删除、也不自动改成原生归档。

未归类和时间未知是不同维度。它们都保留原生搜索、已知查找、当前上下文入口及初次整理预览的可达性；不增设常驻“其他主题/其他对话”或日常待审队列。**查找可达必须真测，不能把看不见当做整理成功。**

### 3.1 成立和归属的判断顺序

1. 已核验scope、原生对象及内容使用授权是门槛，不是语义分数。
2. 人工新建/归属/排除/锁定、从主题内发起的CreationIntent优先。
3. 明确且可验证的接续/分支、命名对象、成果目标支持同一事项。
4. 经授权的用户输入/稳定标题/别名支持语义候选；原生Project名仅弱先验。
5. 时间相近、同开标签、共享工具或泛类别词，不足以证明共同工作目标。

对话内容逐渐转题时保留主身份和既有Placement；提供相关片段或建议新增归属，不因最后一条消息静默迁走整个窗口。多主题对话允许多Placement，但用户点击的主题语境必须随导航保存，不能由列表第一个成员反推。主题稳定ID不随名称/模型/时间重生成。

### 3.2 过多窗口不自动拆主题

同一目标的大量窗口：先处理局部查找、近期容量、旧窗口、系列与工作集。只有出现**独立成果/目标、可稳定区分的成员子集以及用户分别继续工作的实际需要**，才建议拆分。20或50个窗口不是拆分阈值；2个不同工作目标也可以值得拆。

合并需证明同一事项、重复组织成本高且无冲突的人工语义；同名、同Project、主题卡数量过多都不是充分理由。建议不影响当前布局，接受前展示成员变更和冲突。

拆/合使用RestructurePlan：以当前scope、目标revision、成员与负约束hash为预条件。合并由用户选保留主题ID，旧ID保留重定向/别名与审计；拆分保留原主题ID供用户选定的主部分，新增主题获得新ID。人工显示名/锁/图标不丢失，工作集/片段仍指向原conversationId。排除冲突逐项确认，未确认时排除优先；不能借合并洗掉负约束。

所有重组是单一逻辑提交，分区状态用写时复制/已校验根切换，不全库旧快照回滚；撤销只应用安全inverse并检测后续人工修改。多个新建目的地冲突时回到“询问”，不按时间选一个Project。原生数据没有对应的自动搬移。

## 4. 自动识别算法：明确可实现底线与质量门槛

基线D1/D2只是`experiments/d12/rules.mjs`的严格中文模板匹配，限定唯一已知主题、仅影子预览、16.67%合成覆盖；不是通用语义聚类，也没有运行时新主题发现。

新流程：证据授权/角色/去重 → 最小EvidencePack（对象、目标、任务、明确前序、缺失）→ 词法/用户别名/已确认系列召回 → 可选语义召回 → 约束后重排 → EXISTING / NEW_THEME / MULTI_TOPIC / UNKNOWN。初始top-20只作为计算预算候选，不是最优值。

EXISTING先验证硬约束，再用独立校准集上的误差-覆盖曲线设自动阈值和与次候选的分差；不能直接使用模型自报confidence。人工发起归属是确定性路径，无需语义推理。已有人工组织不自动重写；新主题/拆合默认预览，只有后续独立审批和质量证据才可讨论静默创建主题，原生Project写入永不由模型建议直接触发。

输出必须含实际证据ID、理由类别、冲突/未知、baseRevision和model/policy/evidence版本，不能输出任意工具指令或原生写入权限。输入中的“自动帮我移动所有项目”等文本在此只是待分析数据，不是授权。

中文/中英混合样本必须包括同名不同事、不同名同一事、否定/转述、单窗口事项、短暂插曲、共享Project、长对话换题、单目标几十窗口、多主题分支。D1独立标注、按用户/事项/系列/时间隔离，D2报告自动覆盖、误合并/误拆分、纠错复发与稳定性；98%归属精确率/90%标题接受仍是待验证目标，1200模板不自动继承认证。

## 5. 自适应区间：直接试候选跨度，不按“月活数×比例”推算

### 5.1 纯日历投影

有效跨度H∈{7,14,30,60,90}；当地日期T与IANA时区Z固定在视图会话中。段k≥0：

`W(k,H,T) = [T+1−H(k+1), T+1−Hk)`，按当地日历日期运算，不按H×24小时。

主题在候选H下取最近可靠新用户发送落入唯一一段。共享Project必须证明发送者是当前个人scope对应的用户；仅有role=user不证明是本人，协作者输入不自动计入个人活跃。作者未知单列UNKNOWN，不用主题归属代替作者证据。存在无冲突的窗口内正向事件可证明当前段；判断历史段还需排除更晚发送缺口。成员依其父主题段分近期/旧/未知，使用同一(H,T,Z,evidenceRevision)，不能父卡用30日、子行用7日。

上下每次移动一个H日区间；k=0不渲染向上；空段不暗中跨越。H改变不修改主题/成员/证据，不写访问、分类或创建时刻为新发送。手工工作集、固定、当前历史对话和创建中的对象只是可达例外，不伪造活跃。

### 5.2 密度证据与候选比较

对每个候选H实际计算**不同稳定主题ID**在最近H日的数量N(H)，不计窗口数量、标签页、快捷入口、影子建议、空主题或同主题的重复显示。内容很多但同一主题仍计1。显式隐藏/退休主题按用户显示规则排除，原生固定及待处理状态不归密度控制。

不要线性外推“月活2个→90日6个”，也不要宣称缩到7天必能少于10个：如果24个主题近7天全活跃，任何候选都无法降低数量，应保留导航完整性而非硬藏主题/改聚类。

密度基于**当前已知且获授权的工作区总体**，不是未知的全账户历史。对候选区间，记录可证活跃数L(H)、时间未明的潜在数U(H)−L(H)及发现范围/漏项说明；未发现范围无界、未归类活动会改变主题总体、正在大批导入时，不能推断“低活跃”。保守实现先要求候选比较所涉总体和计数均有完整证据；后续可用区间上下界证明所有可能值导出同一决策，不能用一个任意“可信度90%”替代。

有意义的覆盖不足时：保持既有H，首次为30；用户仍可手动固定任一H。PR #14的originalUserSentAt/TimeCoverage仍UNKNOWN，因此**生产自动密度尚不能启用**；增加H选项并不能修复时间来源。

### 5.3 可实施的选择器候选P28-A（参数均待评审/验证）

初始舒适区间[5,10]是试验假设，不是用户硬配额或真实均值。对完整的候选N(H)：

`loss(n) = 2×max(0,n−10) + max(0,5−n)`。

先保留当前H，只在某个候选明显改善loss时考虑变化。取最小loss的候选，平局先保留当前H；当前不在最优集合时选离当前H的`abs(log(H/Hcurrent))`最近者；仍平局选接近30者。改善通常必须`oldLoss−newLoss ≥ max(2, 0.25×oldLoss)`；当前N(H)=0且候选能新增至少1个已证主题时，最低收益改为1（此特殊情形不再取25%门槛的较大值），仍须满足全部覆盖/抗抖条件。所有跨度都为0则保持当前值，不造主题填空。

这样优先解决拥挤而不过度追求填满：若90日也只有同两个主题，与30日一样，则不为了凑卡片强行扩展。候选例子和边界见[验收矩阵](research/V28_BASELINE_AND_ACCEPTANCE.md)。不得把这些参数包装成已完成用户研究。

### 5.4 抗抖动与范围变化

首次有充分数据的整理预览可以展示一次建议H并由用户接受；数据不足保持30。持续自动模式最多每7个当地日评估一次，须两个相隔至少7日的有效评估推荐同一H，并满足上述收益，且最近一次自动应用已满14日。批量导入、主题拆合/大范围人工重组及证据大规模撤回后进入7日冷却，重新积累有效观察；不是靠新的主题数量立即反馈调H。

每日密度历史应保存当日获证实的小型汇总，或用当时截至时刻的完整发送事件重算。**不能把今天的“最后一次发送”套回过去日期，伪造过去的活跃密度。**

决策仅产生pending推荐。自动应用在新进入工作区的安全边界：非编辑/拖动/菜单操作、非原生输入/生成冲突、没有当前历史浏览需要保持。现有tab固定自己的(H,T,Z,policyRevision)，但新的可靠发送/撤权仍可在固定边界内原子更新归属展示，保留正在看的引用而不制造重复卡片；不因另一tab采纳新H跳页；新会话用已提交的新策略。当天午夜/时区变化也不在当前历史浏览中偷偷改锚点。用户明确刷新/选择新跨度时保留当前对象/时间锚，并说明这是新的浏览段，不沿用旧k数字。

应用后可有一次短暂“已调整显示范围 · 撤销”，不显示永久时间标签；撤销回到原H并切为用户固定，直到主动重新开启自动。手动选择立刻优先、跨重启保留，不周期性游说用户恢复自动。
