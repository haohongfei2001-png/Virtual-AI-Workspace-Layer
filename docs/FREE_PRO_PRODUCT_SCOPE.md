# VAIWL Free / Pro 产品范围与首次交付合同

状态：2026-10-13 最新用户方向，分级与 Free 优先开发已明确；本文是既有 v2.8 候选的范围修订，不是另起项目或收费/账户上线授权。唯一执行计划仍为 [DEVELOPMENT_PLAN](DEVELOPMENT_PLAN.md)。原设计方案中的 AI 主题、系列、多Project关联、派生名、人工纠错与模型实验予以保留，但按下文归入 Pro 的后续阶段；不删除历史代码、资产或测试。

## 1. 产品分级是同一个代码库的两条交付路线

**Free：原生 Project 工作空间。** VAIWL 页面、主题卡片、连续侧栏、无字阅读返回、历史分段以及原生输入和工具保持现有视觉/交互基线。每张正式主题卡严格对应同一已核验账户/组织下的一个真正 ChatGPT Project；唯一键为 (scope, nativeProjectId)，标题为当时观察的原生 Project 名。Project 内窗口只能来自该 Project 的已核验 ConversationRef，行标题只用其原生聊天标题。相同名称的两个 Project 绝不能合并；名称变化随可信原生观察更新，派生主题不能在 Free 中覆盖它。

**无 Project 窗口同等重要。** Free 主工作空间始终有“未加入项目的聊天”独立列表/区域，使用原生聊天标题，不把该列表冒充一个真实 Project，也不为其生成自动主题。最近未归项目聊天和较早聊天都可通过现有时间导航/展开/查找抵达。已明确属于某Project的聊天不重复显示在无项目区域。无法确认原生Project归属的已知引用不能假装原生无Project，应作为“归属待核对”的可达记录显示，并尽快核验，而不是从工作区消失。

**Pro：在完整 Free 基础上叠加 AI 虚拟组织。** Pro 主要对已确认 nativeProjectId=null 的聊天提出虚拟主题及派生聊天标题，允许自动收录与智能命名；不迁移/修改真实 Project/聊天，不复制对话正文。虚拟主题以独立命名空间/ID和内部标识表示，绝不使用真实Project ID或显示成真实项目。Pro 的未归类剩余窗口仍按原生标题可达，不会因为模型未读到、错误或拒绝而消失。AI 也可以保留原设计中的系列、关系、多Project派生研究和受控人工纠错，但它们不是 Free 的开发/发布门槛，也不得侵入原生Project成员的默认显示。

此处 Free/Pro 是 **VAIWL 自己的产品功能分级**，不等于 ChatGPT Free/Pro、账号身份或原生Project权限。用户持有哪种ChatGPT计划不得被VAIWL凭昵称猜测；收费/会员鉴权未在本轮实施。

## 2. Free 的完整日常流程

打开真实ChatGPT后，VAIWL在有可靠scope和宿主能力的条件下枚举可访问的原生Projects及已知聊天引用，分为真正Project和无项目聊天；按可靠用户实际活跃度排序、分段和持续校正。可以进入原生Project、原生聊天，在Project内使用原生“新聊天”，从工作空间触发新Project入口时遵循已验证的原生能力、明确用户动作与相应权限；不能从虚拟主题生成一个同名项目并称成功。

原生聊天/Project名称、原生搜索与所有工具仍原生，不加入 Free 自有“AI命名”“派生重命名”或手工虚拟拆合的默认编辑器。使用原生重命名入口不受限制：它改变的是ChatGPT自身对象，下一次可验证观察反映新标题；VAIWL不自行代理发送或调用未证实的原生项目API。已有工作集/备份/历史逻辑是基础设施，可复用，但不会生成额外的Free主题或派生名字。

新聊天/用户实际发送发生在原生Project或无项目范围时，应即时更新显示；未发消息的空白新聊天仅临时进入当前工作现场，不能被写入为可靠UserSendEvent，更不能永久使所属Project活跃。刷新、SPA前进后退、切账户、跨tab、worker重启都应保持原生完整，避免已知聊天突然从所有入口消失。

## 3. 活跃度：准确性和可用性同时为硬性要求

**两种事实必须独立保存：**
- 可靠“用户原始发送”证据（sender、conversation、message/branch、timestamp、来源与覆盖），用于有证明的时间分段。
- 仅供可逆界面排序的“观察/近似活动”证据（已确认当前用户的新发送动作、可核验原生最近活动信号、首次观察、是否仅打开空聊天、数据新鲜度、缺口），有来源与TTL；**不能写入UserSendEvent.sentAt或宣称证明无更晚发送**。原生updated_at、访问时间、AI回复、项目改名/文件变化都不得无条件当作用户发送。

Free 必须同时实现：
1. **最近事件立即显示。** 一次已确认的Project内新发送可直接显示为最近活动；刚新开的无消息窗口只作短暂会话例外并自动消退，不凭空产生长期活动。
2. **较早项目自动下沉。** 已有可靠最近发送落在两个月前的Project，在30日视图不应无限留在最近。与该时间相比若缺少后来变化的完整覆盖，则可进行“暂定较早”的可逆展示，但不能假称完整历史已证。
3. **发现资料不完整仍显示。** 缺时间/缺覆盖/断连时，项目不能永远卡在一种UNKNOWN队列里；使用证据等级、最近核验、有限宽限与可撤回近似规则维持可用排序。所有已知Project与聊天始终可以经普通界面/查找抵达，不能暗藏、删除或显示为空库。弱排序只影响默认位置，不修改数据、状态或强行“正式归档”。
4. **持续校准。** 先使用本地已知信息渲染，再异步做有界校验；新证据推翻旧排序后自动更正，不抢焦点/清空输入/改变用户正在看的段。新浏览器会话与访问后有明确的重新校验点，不能永久依赖第一次导出。
5. **真实跨设备局限诚实表达。** 扩展没获得手机等其他端的可靠活动来源时，无法保证即时知道远端新消息。要满足真实活跃度验收，必须证明相应宿主/渠道刷新能发现它；缺渠道时Free可维持近似列表，但“跨设备准确”不得标已通过。

**证据标签与呈现分开：** 内部区分 CONFIRMED_RECENT / PROVISIONAL_RECENT / CONFIRMED_OLDER / PROVISIONAL_OLDER / UNRESOLVED 等状态；界面仍是最近/较早和全部可达，必要时在详情/诊断解释“为何排序”，不在每行常驻时间、置信分、来源或计数。不能凭弱证据把某Project宣传为确定不活跃，也不能因不确定而无限置顶。最近/较早的时长可先用当前可靠的30日模式，支持明确手动跨度；自动7/14/30/60/90仅在有效库存与时间证据足够时启用。跨度变化不改变原生归属、主题身份和正在使用的工作集。

## 4. Free/Pro 变体与数据所有权

统一事实层包含Scope、NativeProjectRef、ConversationRef、nativeProjectId（已确认ID / 确认无项目null / 未知三态）、ProjectMembershipEvidence、ActivityEvidence与ObservationFreshness。Free视图只从这些已核验事实生成；把真实Project/无项目误判成另一个Project属于关键失败。

Pro 可以另外拥有 VirtualTopic、VirtualPlacement、DerivedConversationTitle、SuggestionBatch和ManualOverride；此类ID及索引与原生Project严格分开。同一无项目ConversationRef同时在本地存在虚拟关系，并不等于在ChatGPT内已进入Project。Free→Pro只添加派生投影；Pro→Free立即恢复原生名称与原生项目/无项目清单，既不破坏原生内容，也不删除Pro人工作品和可导出资产。再升级可以在同scope、数据授权仍有效时恢复Pro视图。禁止把Free的读取、查找、备份、账号隔离、安全恢复放进付费门槛。

Pro 模型读取正文/用户输入、端侧模型、云端推理、会员系统与计费分别需要授权和质量验证；不能把现有D1/D2的1200模板/16.67%覆盖当成自动虚拟收录准确率。Pro的自动归类应先shadow/建议，再以独立自然中文标注、误归类/漏归类和用户纠错成本证明质量后才可启用自动应用；人工排除/锁定高于AI，关闭AI有立即的原始入口。高风险真实原生写入不随Pro订阅自动开放。

## 5. Free 优先，不以 Pro 或外围功能拖延

沿原A–G**一份正式DEVELOPMENT_PLAN**执行，当前所有开发资源优先放在Free。建议依赖顺序：
- **Free 入口真实性**：真实ChatGPT scope、Project稳定ID/名称、chat membership和未加入Project聊天的可发现范围；有权限缺口时不伪全量。
- **Free 活跃可用性**：可靠事件、观察型活动、自动时间下沉、旧聊天刷新与跨设备活动纠正；记录误判/延迟/无法判断的真实测试。
- **Free 完整交互**：已批准v2.7视觉、原生Project/无项目清单、排序/时间/阅读返回、无AI原生标题、快捷键/输入/工具完整可用。
- **Free 稳定交付**：B4/B5恢复、历史/未知可达、项目迁移/删除/名称变化、账户隔离、真实宿主与实际PAIA共存、性能及发布渠道约束。
- **Pro 后续**：完成Free门槛以后，再在保留的D1–D5/B3/C/F/E研究基础上实施虚拟收录、命名、系列/拆合、人工纠错、质量与受控AI推理。Pro不能阻塞Free修复。

**Free不是“所有自动分类算完后的降级开关”，而是第一款独立可完成的产品。** 只有真实宿主的入口、成员、活跃体验和原生保留通过，才宣布Free交付；合成Chrome 100k、旧v2.7的50/50及访客部分实验均不能单独满足。不能因为真实时间证据未知就无限推迟可用投影；但也不能用虚假时间或丢失记录制造漂亮演示。

## 6. 与 v2.8 前一版候选的定向关系

此前 [CORE_MECHANISMS_V2_8](CORE_MECHANISMS_V2_8.md) 对自由Workspace、多Project派生归属、主题拆合和AI建议的设计**保留为Pro能力储备**，不再作为Free的默认对象模型；“主题第一次新开就要求创建同名Project”被简化为“Free主题本来就是原生Project，项目内新聊天沿用原生Project；新增Project使用原生途径和明确用户动作”。前一版H自适应机制可被Free复用，但以活动证据足够为开门条件，不依赖AI。用户本次方向优先于PR #15早先待审D28默认。过时段落只作保留的Pro候选，不构成Free验收标准。

所有旧源码和历史结果保留；由新范围重新排列工程阶段，而不是删除Pro研究。完整Free/Pro验收要求见 [分级验收矩阵](research/FREE_PRO_ACCEPTANCE.md)。
